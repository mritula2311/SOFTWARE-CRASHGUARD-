Numbers are in `results/results.json` (keys given) and in `docs/03_results/REDESIGN_A_RESULTS.md`, `REDESIGN_B_RESULTS.md`, `XSIM_VERDICTS.md`. Every table rests on the constants of `docs/03_results/ASSUMPTIONS.md`. Where an answer is a limit, it is stated as one.

**1. Is the simulator valid?**
Not shown. The custom simulator is an abstraction (static shadowing, a capture rule, an assumed loss model). It was compared with ns-3 (lorawan module) on 16 baseline cells: 15 agree within 5 points, one is 5.4 points out, so the pre-stated criterion was **not met** (`XSIM_CALIBRATION.md`, `rd.x1.*`). The calibration was also run with both simulators at ns-3's shipped (7 dB better) gateway sensitivity: the criterion is not met there either (largest difference 7.9 points, `rd.x1.b.*`). On the D1 comparison the two simulators give different verdicts for H-D1a and H-D1b (`XSIM_VERDICTS.md`, `rd.x13.agree.*`); D1's gain is therefore reported as simulator-dependent, and by the rule fixed in advance D1 does not go to the main paper. No result is validated against a real radio. Open: the comparison with the three published simulator papers (X1.4) was not run.

**2. Is D1 (or D2) just prior work?**
Possibly in part. Retransmission limits and ACK timeouts are in the LoRaWAN rules and in Khan et al. (full text read); an adaptive-retransmission paper for mines (IEEE CNS 2020) could not be opened and may overlap with D1; aggregated and group ACKs listing devices exist for LoRaWAN (A2S2-LoRaWAN, DG-LoRa; abstract level) so D2 does not own the aggregation. What D1 adds is stated as a combination (per-class deadlines, duty budget, Beta loss estimate, load index, one offline table), not as a unique idea (`docs/06_references/CLOSEST_PRIOR_WORK.md`, `NOVELTY_SCAN.md`). Absence statements read "no study found in the sources checked" with the sources listed (IEEE Xplore, Scopus, Google Scholar and TRID were not run; OpenAlex returned HTTP 503).

**3. There is no hardware.**
Correct. Every protocol number is SIMULATED or ANALYTICAL. The firmware decision path was run in a host build against the Python reference (0 mismatches in 10,000 random histories and in replayed simulator decisions, `rd.d6.*`); ESP32 flash, RAM, timing and an emulator run are NOT_RUN. A bench protocol with logging hooks and a parser for the two-stage alert is ready (`docs/08_hardware/R3_BENCH_PROTOCOL.md`); the hardware row is NOT_RUN until the author supplies logs.

**4. Are the baselines strong enough?**
Six baselines are used and every D-hypothesis against the best of them per cell where stated (H-D1s): the severity table, UA-SCT, fixed 3 retries, quick retries, Tamang-style slots, Khan-style retries. On FRESH-A with the six baselines D1 beat the best one by +0.031 on average but only narrowly in some cells (`rd.fa.d1s.*`). A Nessa-style baseline (adaptive ACK timeout from the airtime plus a redundant retransmission; implemented from a secondary description because the CNS 2020 paper could not be opened; tuned on the DEV grid only; ADDED-AFTER-SESSION-1) was then added: D1 is better than it by +0.050 on average and in 75% of the cells, but it is the best of the seven baselines in 17 cells and H-D1s with seven baselines is not met (`rd.fc.*`). D1 is better than quick retries by about 3.6 points, and quick retries are what most of D1's gain over the weak severity table consists of. On the cross-simulator scenario H-D1s is not met in either simulator. Standard LoRaWAN confirmed uplink (NbTrans 8, ACK in RX1 or RX2) was added in ns-3 (`rd.x13.ns3.mean_delivery.lorawan`); ADR on was not run; no adaptive scheme from the literature could be implemented from the text read. The severity table is a weak baseline in the custom simulator (it waits 5 s before the initial Critical send); this is stated in `REDESIGN_A_RESULTS.md`.

**5. Was anything tuned on test data?**
No. Each redesign has three data roles (diagnosis on old grids, development on a new grid with at most 5 logged iterations, one fresh grid drawn from a hash after the code was frozen; `PREREGISTRATION_V12.md` sections 1, 5, 10.5). The freeze files and grids are `results/tables/rd_frozen_A.json`, `rd_fresh_A_grid.json`, `rd_frozen_B.json`, `rd_fresh_B_grid.json`, committed before each run; each run writes a marker and refuses a second run. The DEV log is `results/tables/rd_dev_log.csv`. Disclosed limits: the simulator files changed after the FRESH-A freeze (D1 and D1 + D2 reproduce the stored delays bit for bit, `test_rd_regression_a.py`); the cross-simulator run re-used the SF9 cells of FRESH-A (a cross-check, not a second held-out test); DEV and FRESH share the finite pool of real class pairs (V12 addendum A 5f).

**6. The data are synthetic.**
The simulator's events are drawn from real out-of-fold class pairs and real early-exit decision times of the VZCrash test events (MEASURED_SOFTWARE pools); arrivals, geometry, losses and bursts are simulated. No synthetic crash pulse is used: no generator passed the realism gate (`DIAGNOSIS_SYNTH.md`), so D5 used no synthetic data. Crash rate (0.1 per vehicle-hour) and burst sizes are stress values, not real rates.

**7. Are the statistics sound?**
Paired bootstrap over events within cells (2,000 resamples, seed 42), made more conservative by also resampling simulated hours (the verdict uses the larger p and the smaller bound), an intersection-union rule for bounds that must hold in every cell, and one Holm family of ten hypotheses with final adjusted p-values (`REDESIGN_B_RESULTS.md`). Every effect has a 95% interval. Limits: the hour-cluster bootstrap still treats hours as independent; one-sided criteria with margins were chosen before the runs; with 100 to 600 hours per cell the intervals are narrow and describe the simulator, not the world.

**8. Dataset leakage.**
Splits are by group (recording), with the dedup and strict-test checks of the earlier rounds (`docs/04_audits/`, `docs/00_overview/PROJECT_STATUS.md`); VZCrash has no vehicle identifier, so the most independent grouping available is used and the choice is in `DECISIONS.md`. The redesign round uses stored test-split decisions and does not refit any model. The dataset events were pre-selected on the device; this is a stated limit.

**9. Can it be reproduced?**
Seed 42 and fixed seeds per grid; pinned requirements; the redesign commands are in `docs/05_data_code/REPRODUCE.md` and the module docstrings; the freeze hashes are in the freeze files. Environment limits: the ns-3 build is in WSL outside the repository (versions, commits and local patches in `XSIM_BUILD.md`); the system Python (numpy 2.x) was used for the redesign work, with three old tests failing on a numpy attribute; ns-3 runs are not bit-identical across machines. About 0.2% of ns-3 runs crashed inside the module and are dropped for all policies (`rd_x13_ns3_dropped.json`).

**10. What are the deployment limits?**
No road test, no real radios, no ESP32 timing. Duty-cycle limits are parameters (the 10% for 433 MHz in India is the limit of rule 3 row 1 of G.S.R. 347(E), 2022, read in full on 2026-11-16). Hostile conditions are checked only in bounded models (H-D2c: two vehicles, small bounds; a stolen gateway key is outside the claim). The D1 table is about 187 kB per base SF; the C path uses double precision and needs a float or fixed-point port for the ESP32. Vehicle-to-vehicle overhearing is rare in the simulated channel, which is why D3 had nothing to act on. A crash alert system built on these results would still need field tests.
