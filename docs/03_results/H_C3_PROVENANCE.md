## What the original fit read

| Step | Code | Records read |
|---|---|---|
| Descriptors of the real pulses | `src/crashguard/fin_c.py`, function `real_desc` (reads `data/processed/pp_pool.joblib`) | all 913 pooled records: development 543, validation 184, sealed 186 |
| Generator fit and calibration | `fin_c.fit_params` calling `fin_synth.fit` and `fin_synth.calibrate` on that table | all 913 (file `results/synthetic/generator_params_all913.json`, SHA-256 `6c6fa914d29927d075b61f1d545d26a1cc72c1a7e01af72b933d240162beb55f`) |
| Fidelity check (KS, five descriptors, at most 0.20) | `fin_c.fidelity` | the same 913 records (in-sample) |
| Real smallest range for the comparison | keys `p.b2.<mode>.smallest.config` | the pooled records; a result to compare with, not something the generator was fitted to |

Consequence: the stored verdict (`f.holm.hc3.verdict`, SUPPORTED for the frontal barrier mode, the fidelity check passed for frontal barrier and other) is an in-sample result with respect to the validation and sealed folds. The paper therefore uses only the refit below.

SHA-256 of the sorted record identifiers of the development fold (from `SYNTHETIC_PROVENANCE.md`): `9569410d54565e877108ece1f15f9663f1bca24e962c073c9098e9fa7f083a4b`.
